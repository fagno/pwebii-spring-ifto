== Aplicação WEB

Uma aplicação web oferece recursos por meio de um servidor e permite que o usuário os acesse em um navegador. Esses recursos podem ser páginas HTML, imagens, arquivos ou respostas com dados. Neste material, estudaremos principalmente a comunicação feita por HTTP e HTTPS.

Em geral, o usuário não precisa instalar a aplicação em seu computador: o navegador envia uma requisição ao servidor e apresenta a resposta. Isso facilita o acesso por diferentes sistemas operacionais, embora a aplicação ainda dependa de um navegador compatível e de uma conexão com o servidor.

Ao longo do curso, criaremos páginas e funcionalidades executadas no servidor com Spring. Para entender esse fluxo, começaremos pelo papel do cliente, do servidor e das mensagens HTTP.

== O que o seu servidor web faz?

Uma aplicação web segue o modelo cliente-servidor. O cliente envia uma requisição para um recurso identificado por uma URL; o servidor a processa e devolve uma resposta.

Por exemplo, ao abrir uma página de pessoas, o navegador pode enviar `GET /pessoa/list`. A aplicação consulta os dados e responde com o HTML da listagem. Em outra requisição, o servidor pode devolver uma imagem, um PDF ou dados em JSON.

A resposta contém um código de status. `200 OK` indica que a requisição foi atendida. `404 Not Found` indica que o recurso solicitado não foi encontrado. O status ajuda o cliente a entender o resultado, mesmo quando a resposta possui um corpo com mais detalhes.

== O que um cliente web faz?

O navegador é um exemplo de cliente web. Ele permite que o usuário informe um endereço, siga links e envie formulários. Para isso, constrói requisições HTTP, recebe as respostas e interpreta o conteúdo que sabe apresentar, como HTML, CSS e imagens.

Neste capítulo, *cliente* normalmente significa o navegador que age em nome do usuário. Usuário e navegador têm papéis diferentes: o usuário escolhe a ação; o navegador realiza a comunicação necessária e apresenta o resultado.

== Os clientes e os servidores conhecem HTML e HTTP

HTML (_HyperText Markup Language_) organiza o conteúdo de uma página, como títulos, parágrafos, links e formulários. O navegador interpreta esse documento para apresentar a interface ao usuário.

HTTP (_Hypertext Transfer Protocol_) define a comunicação entre cliente e servidor por requisições e respostas. Uma resposta HTTP pode transportar HTML, mas também pode transportar outros tipos de conteúdo. O cabeçalho `Content-Type` informa o tipo enviado; por exemplo, `text/html` indica HTML.

Em outras palavras, HTTP é o protocolo de troca das mensagens e HTML é um possível conteúdo da resposta. O servidor não precisa enviar HTML em todas as respostas.

.Os clientes e os servidores conhecem HTML e HTTP? - fonte [1]

Considere a sequência: o navegador envia `GET /pessoa/list`, o servidor responde com `200 OK` e um documento HTML, e o navegador exibe a página. Se essa página referenciar uma imagem, o navegador poderá fazer outra requisição para obtê-la.

== Protocolo HTTP

HTTP é um protocolo da camada de aplicação. Ele define, entre outros elementos, métodos de requisição, campos de cabeçalho e códigos de status. Na web, as mensagens são transportadas pela rede usando as tecnologias da pilha de protocolos da Internet.

O endereço `https://` indica o uso de HTTPS, que protege a comunicação por meio de TLS. O formato das requisições e as ações dos métodos HTTP continuam relevantes nos dois casos.

Cada requisição tem uma resposta correspondente. As mensagens podem passar por intermediários, como proxies, antes de chegar ao servidor ou ao cliente. Para acompanhar os exemplos deste curso, basta reconhecer o fluxo navegador → requisição → servidor → resposta → navegador.

== O HTML é parte da resposta HTTP

Uma resposta HTTP contém um código de status, campos de cabeçalho e, quando aplicável, um corpo. Quando o servidor devolve uma página, o HTML fica no corpo da resposta.

Considere esta resposta simplificada, usada apenas para identificar suas partes:

[source,http]
----
HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8

<h1>Pessoas</h1>
----

A primeira linha apresenta o status. O cabeçalho identifica o tipo de conteúdo. Após a linha em branco, começa o corpo com o HTML que o navegador interpretará.

== E o que consta na solicitação?

Uma requisição informa a ação desejada, o recurso de destino e campos de cabeçalho. Dependendo do método e da ação, ela também pode conter um corpo. Nos formulários e páginas deste curso, os métodos mais frequentes serão GET e POST.

*GET* solicita a representação de um recurso. É o método adequado para abrir páginas e consultar dados sem pedir uma alteração no servidor. Parâmetros de busca podem fazer parte da URL, como em `/pessoa/busca?nome=Ana`.

*POST* envia dados para que o servidor processe uma ação. Ao cadastrar uma pessoa, por exemplo, o navegador pode enviar o formulário para `POST /pessoa/save`. No exemplo de Spring deste material, a exclusão também é realizada por POST, pois altera os dados.

.Post - fonte [1]

GET e POST podem transportar informações de formas diferentes. Parâmetros de uma consulta GET geralmente aparecem na URL; dados de um formulário POST geralmente são enviados no corpo da requisição. O método escolhido deve refletir o objetivo da operação, e uma ação que altera dados não deve ser disparada simplesmente pela abertura de um link GET.

POST, por si só, não torna os dados secretos. A proteção da comunicação depende de HTTPS; o servidor ainda precisa tratar corretamente os dados recebidos. Além disso, URLs podem aparecer no histórico do navegador ou em registros de acesso, portanto não coloque senhas em parâmetros da URL.

== Páginas Dinâmicas ou Estáticas

*Conteúdo estático* é servido, em geral, a partir de um arquivo já disponível, como uma imagem, uma folha de estilos CSS ou um HTML pronto. Para a mesma versão do arquivo, seu conteúdo não precisa ser montado especificamente para cada requisição.

*Conteúdo dinâmico* é produzido ou selecionado conforme o processamento da requisição. Uma página de listagem, por exemplo, pode ser montada com os nomes consultados no banco de dados naquele momento. O resultado também pode variar conforme parâmetros enviados pelo cliente ou conforme o usuário autorizado a acessá-lo.

Os dois tipos podem coexistir na mesma aplicação. Nos próximos capítulos, o link:../spring/[Spring MVC] atenderá as requisições e produzirá páginas com Thymeleaf; o link:../jpa/[JPA] será usado para acessar dados persistidos. Imagens e arquivos CSS poderão continuar sendo servidos como recursos estáticos.
